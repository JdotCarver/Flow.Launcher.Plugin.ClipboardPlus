# README.md — Synthetic performance baseline

Run on Windows with .NET 9: `dotnet run --project tools/performance-baseline/PerformanceBaseline.csproj -c Release`.
The program uses generated text and pixels and temporary SQLite databases; it does not access the real clipboard or plugin data. It warms each scenario once and reports five repetitions, process-wide managed allocation and a working-set snapshot. SQLite figures include database creation, insertion, read, closing and deletion; they are not startup timings. The GC scenario is isolated, not end-to-end copy latency. Bitmap encoding is synthetic. Results depend on machine load, disk, runtime, and ordering; compare runs on the same machine and do not interpret working set as Flow Launcher's memory consumption. This harness does not exercise fuzzy search, the Flow Launcher UI, live clipboard events or real startup; those require separate integration measurement.

Additional scenarios separate image hashing by image entropy, and prepare temporary databases outside the timed restore loop before reopening and materializing their records. The live-text measurement reports the managed heap delta after forced collections while retaining records; it is not a leak test or an estimate of native image memory. The database restore scenario excludes the plugin's initialization, expiration cleanup, UI, and Windows history synchronization. No scenario invokes the real Flow Launcher fuzzy matcher, clipboard monitor, or UI. These gaps must be addressed before ranking those paths.

The integration scenarios call the actual plugin query and record-add methods using generated records, a synthetic host and an in-memory record list. They do not initialize the plugin, start a clipboard monitor, open user settings or use the real clipboard. Query numbers include plugin traversal, result creation and the pinned upstream fuzzy matcher described below. Cancellation coverage checks only a pre-cancelled query. Record-add timing excludes the clipboard event and data extraction, and includes the plugin's forced collections. Private-field access makes this an implementation-coupled diagnostic, not a stable plugin API test.

The contended lock scenario deliberately queues a capture-like lock acquisition after a synthetic all-match query has entered the matcher, then releases the query and measures the wait for the record lock. It is a controlled overlap, not a model of normal arrival rates, real fuzzy matching, or full event latency. Repeated-query managed heap delta compares post-GC heap snapshots after warmup and twenty discarded result lists; it excludes native allocations and cannot establish a memory leak. The synthetic text add invokes data preparation and the real list insertion with persistence and caching disabled; it still does not read the clipboard or execute the clipboard event handler.

The integration host now calls the unmodified matching algorithm from Flow Launcher v2.1.4, commit `9fe822b398ad9541a1a35fb1c688a006a27f2f9d`, vendored under `upstream-flow` with its MIT license (only filename comments added). The unused settings-constructor dependency is a minimal stub; the host uses the upstream alphabet-only constructor with `Regular` precision and no alphabet translation. It does not inspect the installed Flow Launcher version or user settings. Consequently this represents that specific upstream version/configuration, not necessarily the user's running version or non-Latin translation settings. Earlier measurements that used a substring stand-in are not directly comparable.

The SQLite A/B experiment uses fresh temporary on-disk databases, the production schema, equivalent insert SQL and the production `Asset`/`Record` conversions. It alternates five 500-record samples with and without an explicit transaction after warming both paths; timing covers insert and commit, not setup or verification. Every sample verifies row counts, orphan count and one known value, and an additional rollback test verifies that neither table retains inserted rows. This isolates a transaction hypothesis; it is not an A/B test of modified production code, and it does not cover encryption, image assets, concurrency or failure modes beyond explicit rollback.
